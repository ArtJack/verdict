**A latent wart in the new tar parser, reported as a risk and not as a finding because no harm follows from it today.** `_tar_takes_value` reads any three-character prefix of a value-taking option as value-taking. Driving it over 43 valueless option names, exactly one collides: `--list` (and `--lis`) is read as value-taking because the table contains `listed-incremental`, so `--list` swallows the token after it. It is harmless because `list` is also a mode, `_mode("t", "list", ...)` suppresses the archive rule for it, and real tar rejects any command that combines list with a write mode - so every path I could construct either yields the same decision or is a command GNU tar refuses. The honest fix, if the maintainer wants the rule to mean what it says, is to test ambiguity against the union of ALL long options rather than the value-taking subset.

**The guard's file classification is evaluated before the command runs.** `git init <dir>` followed in the same line by a write into `<dir>` is judged against the pre-state, where `<dir>` was not yet a checkout. Observed this run in the scratch directory. It does not affect the project checkout, which exists before any command is judged, so it is an observation rather than a finding.

## Notes

**On the four questions this run was asked.**

**Harness versus prompt.** The boundary is drawn correctly and in the right place: the harness owns everything checkable without judgement (`validate.py` enforces enum values, ISO-8601 UTC timestamps, a non-empty `not_tested` on a shipping verdict, `pass` over zero gates, `pass` over a diff no test executed, frozen confidence, computed outcomes), and `tests/test_agent_contract.py`'s thirteen tests check the prompt's *referential* integrity only — that every path resolves, every shouty token is a real enum, every section cross-reference points at something. Not one asserts behaviour, which is right: behaviour is the eval's job. Three rules sit in only one place and should sit in both. (a) The §3 isolation discipline is enforced by the harness for its own subprocesses (`PYTHONDONTWRITEBYTECODE`, `_drop_bytecode`) and asked of the agent in prose, with nothing checking the agent did it — the new eval row checks that the agent *said* it. (b) The contract's §6 claim that `python3 <plugin-root>/src/verdict_mcp/harness.py facts` "runs from any checkout with nothing installed" is asserted only in prose and is false on Python 3.9; `test_every_console_script_it_names_is_declared` checks that pyproject declares the scripts, which is a different claim, and on this machine — with the plugin installed — `which verdict-facts` finds nothing. (c) §6's rule that quarantine re-evaluation on expiry is an action rather than an opinion has no validator rule; the ledger has been empty for several runs, so nothing has tested it either way.

**Eval adequacy.** As it stands the suite can detect a regression in the parts of the contract a fixture was built for, and is blind to the rest. Seven fixtures, fifty scored rows, and the `cause` fixture now has one row that discriminates between two versions of the prompt — proven by the counterfactual in VERDICT-F-52's evidence. Three gaps matter. First, the discriminating row is a term match on report prose, so it scores vocabulary; a rewrite that keeps the discipline and changes the words fails it, and one that keeps the words and drops the discipline passes. The release documents this honestly, and it also documents `trigger-separated-from-cause` decaying in exactly that way — so the new row's failure mode is already on the record, one row later. Second, whole sections have no fixture at all: §0 (the safety gate, project-key resolution, `blocked` when a money-touching project has no profile), §4 (naming the test-design technique), §5 (TDD red-first evidence), §11 (automation and the security pass). Third, six of the seven fixtures were not scored at all this run, so nothing outside §3 was measured even at the level the suite can measure.

**Install from scratch, as a stranger.** The documented path is coherent and the artifacts are real: the marketplace manifest is valid, the installed 0.74.0 cache ships `agents/`, `hooks/`, `commands/`, `docs/`, `standards/`, `templates/` and a complete `src/verdict_mcp/`, the MCP server is correctly described as optional, and the README's "read-only guarantee, honestly stated" section is genuinely honest — it names the Bash guard as a heuristic, says an external audit got past it six ways, and points at the OS as the real boundary. And the contract's first instruction is `verdict-facts`, which a plugin-only install does not put on PATH — the documented fallback exists and works on 3.13, but I hit that friction myself in this run's opening minute.

**Why the second pass.** It is a process gap, and a narrow one — the fixes themselves have been sound in all three cases. The common cause is that each fix was verified against the sentence the finding was written in, rather than against the behaviour the finding was about. Run 10's own lesson names it for F-42 ("a fix that passes only the reported spelling has been tested against the sentence, not the behaviour"), and this run found the same shape twice more: the mutation campaign enumerated its mutants from the tests just written, so it could only confirm the rules already watched; and the instrument control was written to describe the fault rather than tested against it. It is not coincidence: three consecutive releases, three instances, and each found by varying an input the author did not choose. The countermeasure is already in the project's own lessons and is cheap: before closing a finding, name the axis the finding did NOT vary (argument order, boundary, call site versus body, ordering of injections) and test one point on it. That is what produced VERDICT-F-56, F-58 and F-60 this run, in about an hour.
